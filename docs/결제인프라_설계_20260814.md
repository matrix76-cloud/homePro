# 홈프로 결제·정산 인프라 설계서

## ★ 이 앱이 하는 일 (형·카스 2026-09-11 정리 — 코드 보기 전에 이것부터)

- 앱 안에는 **접수자**(일을 올리는 사람)와 **수행자**(일을 받아 하는 사람) 둘뿐이다. 실제 일을 주고 작업 대금을 내는 **원청자는 앱 밖**에 있고, 화면에 등장할 필요가 없다.
- 접수자는 원청자 본인일 수도, 남의 일을 넘기는 소개자일 수도 있다. 어느 쪽이든 앱에서 하는 일은 같다 — **일을 넘기고 소개료(캐시백)를 받는다.**
- 수행자는 작업 대금을 원청자한테 직접 받고, 접수자에게 **소개료만 챙겨 주면** 끝이다. 작업 대금은 처음부터 앱 밖 얘기다.
- **선결제**면 대금이 PG 에스크로에 있으니 완료 시 **우리가 셋으로 갈라 준다** — 수행자 몫 · 접수자 소개료 · 플랫폼 수수료. 수행자가 소개료를 떼먹을 일이 없어서 캐시백 한도가 가장 높다(중장비 30%). "법인통장 미경유"는 나눠 주지 말라는 뜻이 아니라 **우리 통장에 받았다 보내지 말고 PG 분할정산으로 바로 꽂으라**는 뜻이다.
- **30% 한도는 선결제 유도 장치다.** 소개자는 자기 일도 아닌데 자기 돈으로 선결제할 이유가 없어 보이지만, 100만원 넣고 끝나면 30만원이 돌아오니 넣을 만하다. 원청한테 받을 대금은 어차피 받고, 30만원은 앱에서 챙기는 셈이다. 그래서 한도를 크게 잡았다. 원청이 직접 접수해 선결제하면 그 사람한텐 캐시백이 곧 할인이다. 그래서 접수자 자리에 원청이 서든 소개자가 서든 앱은 똑같이 굴린다.
- **선결제가 아니면 당사자끼리 알아서** 한다. 우리는 붙여 주기만 하고 소개료도 둘이 주고받는다. 그래서 한도가 낮다.
- 홈프로도 스카이링크도 이 한 줄이 본체다. 화면·필드·정산식은 전부 이걸 구현하는 수단이다.

## 1. 전체 원칙 (요건에서 확정된 것)

1. ~~단가유형 대금의 직접 PG 결제는 구현하지 않는다~~ → **★확정(2026-09-11 대표님·형): 홈프로도 스카이링크처럼 결제수단에 '선결제'를 두고, 선결제면 대금을 PG에 태운다.**
   접수자가 대금을 결제 → PG 에스크로 보관 → 체크아웃(완료) 시 분할정산 API 로 수행자 몫 · 접수자 소개료 · 플랫폼 수수료(PG+0.5%)로 갈라 지급. 플랫폼 통장은 거치지 않는다.
   선결제가 아니면(현금·카드·포인트·PI) 대금도 소개료도 **당사자끼리** — 앱은 조건 표시만 하고 정산하지 않는다. 소개료 상한도 스카이처럼 결제방식으로 가른다(선결제 높게 · 후불 낮게, 수치는 대표님 확정).
   따라서 아래 "소개수수료 충전금 선차감·이관"(3-4)은 선결제 트랙이 대신하므로 **보류** — 후불 오더의 소개료 보증이 필요하다고 대표님이 정하면 그때 살린다. 스카이링크 pay 도메인(토스 결제·승인·분할정산·24시간 자동정산)을 그대로 이식한다.
   (아래는 변경 전 원문) 당사자 간 대금은 플랫폼 밖에서 오간다. 플랫폼이 돈을 만지는 지점은 아래 4가지뿐이다.
   - 월 구독료 결제
   - 충전금(캐시) 충전
   - 소개수수료 내부정산(충전금 이동)과 그에 대한 플랫폼 수수료 5%
   - 서브몰 결제 대여(플랫폼 수수료 0.5%)
2. **충전금(현금성 예치금)과 포인트(무상 리워드)는 시스템 전체에서 완전 분리한다.**
   - 충전금: 본인이 입금한 돈. 출금 가능. 충전 시점 증빙은 부가세 0원 예치금 성격.
   - H-포인트: 플랫폼이 무상 지급. 출금 절대 불가. 내부 사용(구독료·수수료)만 가능.
   - DB도 잔액 필드 하나에 섞지 않고 원장(ledger)부터 분리.
3. **플랫폼의 법적 포지션 = 결제 중개자.** 지급 주체가 아니라 정산 대금을 보관(에스크로)했다가 전달만 한다. 약관·화면에 "세무 신고 책임은 회원 본인" 명시.
4. **단가유형·소개수수료 거래는 포인트(내부 단위) 단독 결제로 구조화** — 향후 토큰 전환 시 아키텍처 재사용(대표님 8/13: 코인 전환은 오픈 이후, 법적 검토 병행 중).

## 2. 결제 인프라 구성 (PG 스택)

| 역할 | 사업자 | 용도 |
|---|---|---|
| 미들웨어 | 포트원(PortOne) | 결제 요청·취소·웹훅 표준 창구. PG 추가/이관 대비 라우팅 추상화 |
| 카드·간편결제 | 토스페이먼츠 | 신용카드, 토스페이·카카오페이·네이버페이. 빌링키 정기결제 |
| 가상계좌·서브몰 | 헥토파이낸셜 | 가상계좌 채번·입금 웹훅, 서브몰 등록·분할정산, 지급대행 |
| 본인인증 | CP사(다날 등, 포트원 경유) | 보험 가입, 출금계좌 등록 시 휴대폰 본인인증 + 계좌 1원(실명) 인증 |

구현 표준: 프론트·백엔드 모두 포트원 SDK/API 사용. 결제 검증은 반드시 서버(Cloud Functions)에서 웹훅 + 조회 API 이중 확인. 클라이언트 결과만 믿지 않는다.

## 3. 모듈 설계

### 3-1. 충전금(캐시) 원장 시스템 — 모든 것의 토대
- `wallets/{uid}`: cashBalance(충전금), 잠금액(정산 홀드), 갱신시각. 포인트 잔액은 기존 포인트 시스템 유지(분리).
- `wallet_ledger/{autoId}`: 모든 증감 1건 1행 — type(charge/withdraw/fee_hold/fee_transfer/fee_platform/subscription/refund), amount, balanceAfter, 상대방 uid, orderId, PG 결제 refs, createdAt. **잔액은 항상 원장 합계에서 파생** — 필드 직접 수정 금지.
- 증감은 전부 Cloud Functions 트랜잭션으로만(클라이언트 직접 쓰기 차단, Firestore rules).
- 월 대사(reconciliation): 월간 PG 결제 합계 ↔ 원장 charge 합계 ↔ 잔액 총합 검증 리포트.

### 3-2. 충전 + 증빙
- 카드/간편결제 충전 → PG 매출전표 자동 발행. **공급가액 = 전액, 부가세 0원**(예치금 성격) 세팅.
- 가상계좌 충전 → 입금 웹훅과 동시에 **지출증빙용 현금영수증**(사업자번호 기준) 자동 발행, 역시 부가세 0원.
- 앱 [충전 내역]에서 매출전표/현금영수증 열람·다운로드(PG 영수증 URL 연결).

### 3-3. 월 구독(오더 수락 사용권)
- 1회성 결제(체험권·기간연장) + 빌링키 정기결제(매월 자동 과금).
- 결제 수단 우선순위: H-포인트 선택 시 포인트 먼저 소진 → 부족분만 충전금 또는 카드로 복합 결제(Split Payment).
- `subscriptions/{uid}`: plan, status(active/past_due/canceled), billingKey, nextBillingAt, 결제수단.
- 정기결제 실패·해지 시 오더 수락 권한 실시간 차단(기존 구독 게이트에 연결). 재결제 성공 시 즉시 복구.

### 3-4. 소개수수료 내부정산 (오더 수락 게이트 + 체크인/체크아웃 트리거)
오더 수락 시:
- ① 소개수수료 미설정 → 잔액 무관 즉시 수락.
- ② 정액 설정 → 보유 충전금 >= 수수료면 수락. 부족하면 "충전금이 부족합니다. 충전 후 수락해 주세요" + 충전 페이지 유도.
- ③ 현장견적·견적요청(단가 미확정) → 잔액 체크 없이 수락(후정산). 견적가 확정 후 ①/② 프로세스로 편입.

정산 트리거(빠른선정·비교선정 공통):
- [체크인] 클릭 → 수행자 충전금에서 수수료 선차감(fee_hold, 에스크로 보관). 부족 시 차단 + 충전 유도.
- [체크아웃] 클릭 → 플랫폼 수수료 5% 제외한 금액이 공유자(접수자) 충전금으로 실시간 이관(fee_transfer), 5%는 플랫폼 수익(fee_platform).
- 예: 소개비 50,000 → 플랫폼 2,500 / 공유자 47,500.
- `settlements/{id}`: orderId, 공유자/수행자, 소개비, 플랫폼수수료, 상태(hold/transferred/canceled), 트리거 시각. 오더 취소 시 홀드 반환 규칙 포함.

### 3-5. 5% 수수료 증빙 자동 발행
- 발행 주체: 플랫폼 법인 → 수수료를 낸 수행자에게. 발행 시점: 체크아웃(정산 확정) 시.
- 회원 유형 자동 분기: 사업자회원 → **전자세금계산서**(홈택스/포트원 발행 API) / 비사업자 → **현금영수증**(PG 자동발행 API).
- `tax_documents/{id}`: 대상 uid, 유형, 금액, 발행 상태, 외부 발행번호. 실패 건 재시도 큐.

### 3-6. 무상 H-포인트 사용 통계 (세무 리포트)
- 관리자 페이지에서 기간 지정 엑셀 다운로드: 정산 기간 / 회원 아이디·이름 / 포인트 지급 사유(초대코드·이벤트 등) / 사용된 H-포인트 금액 / 차감된 플랫폼 수수료 / "세금계산서·현금영수증 발행 대상 아님" 표기.
- 용도: 매출이 아닌 판매촉진비(마케팅 비용) 입증. 포인트 원장에 지급 사유 코드가 이미 있으므로 쿼리 export로 구현.

### 3-7. 출금(지급대행)
- 공유자가 쌓인 충전금을 본인 계좌로 출금 요청 → 헥토 지급대행 API로 이체.
- 안전장치: **본인 명의 계좌만**(가입 본인인증 정보 ↔ 예금주 실명, 1원 인증), 자금세탁·대포통장 차단.
- 출금 시 **사업자 간 거래 명세서 자동 생성**: 누가→누구에게 얼마, "과세 사업자 간 거래로 부가세·소득세 신고는 각자 책임" 명시. PDF 열람/다운로드.
- 확장(후순위): 지급 시 사업소득 지급명세서 홈택스 제출 연동.

### 3-8. 서브몰 결제 대여 + 분할정산
- 전문가 입점 시 사업자 정보를 PG 서브몰로 자동 등록(헥토 가맹점 등록 API).
- 전문가가 고객에게 링크 결제 발행 → 통합 결제창(카드·카카오페이·네이버페이·토스페이).
- 고객 결제 → PG 수수료 + 플랫폼 대여 수수료 0.5% 자동 공제 후 전문가 계좌로 직접 정산(분할정산). 플랫폼은 대금을 보유하지 않음.

### 3-9. 본인인증(CP사)
- 트리거 2곳: 보험 가입/제휴 보험 연동 시(실명·생년월일 — 보험업법상 계약 주체 특정), 출금계좌 등록 시(명의 일치 검증).
- 포트원 본인인증(다날 등) + 계좌 실명조회/1원 인증 조합.

3. 소개수수료의 결제 단위: 요건상 "포인트 단독 결제" 구조인데, 정산 흐름은 충전금 차감·이관으로 기술되어 있음 → **충전금(캐시) 차감이 기본이고 H-포인트를 보조 사용 가능**인지, 문자 그대로 포인트 단위 계정으로만 도는지 확정 필요. (토큰 전환 대비 내부 단위 통일 관점)
4. 현장견적·견적요청 후정산의 확정 시점(견적 확정 시 자동 편입 vs 수동 확정).
5. PG 계약 주체·일정(포트원 채널에 토스·헥토 연동 신청 상태).

## 6. 보안 메모

- 8/13 prep-billing에 포트원 관리자 계정(이메일/비밀번호)이 평문으로 게시됨. 리뷰 페이지는 공개 라우트라 **비밀번호 변경 + 해당 글 삭제 권고**. 운영 자격증명은 별도 채널로 전달.
